## 2. 技术路线一：proot（伪 root）

这是本指南采用的方式，也是这批仓库里最靠谱的一类。

### 2.1 freeroot —— 原版

`dxdgame/freeroot` 是 fork，源头是 `foxytouxxx/freeroot`（MIT 协议）。
我们文档 [03-proot详解](03-proot详解.md) 里的逐行分析就是基于它。

核心三行：

```sh
ROOTFS_DIR=$(pwd)                                          # 当前目录当 rootfs
tar -xf /tmp/rootfs.tar.gz -C $ROOTFS_DIR                  # Ubuntu base 解到自己身上
wget -O $ROOTFS_DIR/usr/local/bin/proot ".../proot-x86_64"  # 静态 proot
```

启动：

```sh
$ROOTFS_DIR/usr/local/bin/proot \
  --rootfs="${ROOTFS_DIR}" \
  -0 -w "/root" -b /dev -b /sys -b /proc -b /etc/resolv.conf --kill-on-exit
```

**可用性**：✅ 实测通过（见 [07-实战案例](07-实战案例.md)）

### 2.2 ROOT —— freeroot 的重写版

同一个作者（DeUp Gaming）的重写，换成 Ubuntu 22.04，加了彩色 UI。两个实质性改进：

**改进一：多了 `-b /tmp`**

```sh
# freeroot
-b /dev -b /sys -b /proc -b /etc/resolv.conf

# ROOT
-b /dev -b /sys -b /proc -b /tmp -b /etc/resolv.conf
```

把宿主 `/tmp` 映射进去。好处是 guest 和 host 共享临时目录，编译产物可以直接交换；
坏处是隔离性变差——guest 里 `rm -rf /tmp/*` 会删掉宿主的东西。

**改进二：`env -i` 清洁环境**

```sh
exec "$ROOTFS_DIR/usr/local/bin/proot" ... \
  /usr/bin/env -i \
  HOME=/root \
  TERM="$TERM" \
  PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
  /bin/bash --login
```

`env -i` 清空所有继承的环境变量，只保留三个。这避免了宿主的 `LD_PRELOAD`、
`PYTHONPATH` 之类污染 guest。**这是对的**——我们文档 [06-限制与风险](06-限制与风险.md)
提到过环境变量泄漏的坑，这个写法能规避。

**问题：proot 源不一样**

```sh
# ROOT 用的
wget -O ... https://proot.gitlab.io/proot/bin/proot

# freeroot 用的
wget -O ... https://raw.githubusercontent.com/foxytouxxx/freeroot/main/proot-x86_64
```

实测两个源都活着：

```
https://proot.gitlab.io/proot/bin/proot                              HTTP 200  1,978,448 B
https://raw.githubusercontent.com/foxytouxxx/freeroot/main/proot-x86_64  HTTP 200  1,901,440 B
```

但**大小不同**（1.98 MB vs 1.90 MB），是两份不同的构建。`proot.gitlab.io` 那份
带 debug_info 且未 strip。两者都能用，但不要混。

**可用性**：⚠️ 能用，但 rootfs 源需自行验证（见下节）

### 2.3 REPLIT-24-7-VPS —— 两个 URL 都是错的

```bash
# 第 1 个错误
curl -Lo proot https://proot.me/proot
```

实测：

```
https://proot.me/proot  → 连接失败（DNS 无响应）
```

`proot.me` 是 proot 的项目主页，可能曾经提供过二进制，现在没了。这行会拿到空文件或失败，
后面 `chmod +x` 会报错。

```bash
# 第 2 个错误
curl -Lo rootfs.tar.xz https://github.com/termux/proot-distro/releases/download/v3.16.0/ubuntu-amd64.tar.xz
```

实测：

```
HTTP/2 404
```

这个 release 里没有 `ubuntu-amd64.tar.xz`。proot-distro 的 rootfs 是运行时从
`https://github.com/termux/proot-distro/releases/download/v3.16.0/` 下面按需构建的，
文件名不是这个格式。

**可用性**：❌ 跑不通

## 3. 技术路线二：QEMU 真虚拟机

和 proot 的本质区别：**proot 是假 root（靠 ptrace 拦截 syscall），QEMU 是真硬件模拟。**

proot 里 `CapEff` 是 0，chroot 被禁；QEMU 里你是真的 root，能装内核模块、跑 Docker。
代价是需要 `/dev/kvm`，而且内存翻倍。

### 3.1 通用套路

```bash
apt install -y qemu-system-x86 qemu-utils wget
wget -O ubuntu.qcow2 <cloud-image-url>
qemu-system-x86_64 -m 2048 -enable-kvm -hda ubuntu.qcow2 -nographic
```

想用浏览器访问，加 noVNC：

```bash
apt install -y novnc websockify
websockify --web=/usr/share/novnc/ 6080 localhost:5900 &
```

### 3.2 KVM-SUPPORTED-VPS —— 直链已失效

```bash
wget -O ubuntu.qcow2 "https://download1335.mediafire.com/ylqu0hntg57gXx1mkzy.../ubuntu.qcow2"
```

实测：

```
HTTP/1.1 302 Found
location: https://www.mediafire.com/download_repair.php?flag=4&dkey=...
```

**`download_repair.php?flag=4` 是 mediafire 的"链接已失效"页面。**
mediafire 的直链带 IP 绑定和时效，分享出来几天就死。

正确做法是用官方 cloud image：

```bash
# 结构示例（域名可用性请自行验证）
wget https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img
```

**可用性**：❌ 下载必然失败

### 3.3 IDX-VPS —— 根本没写完

```bash
# [Baqi logic aapke original script ke mutabiq continue rahega...]
# (Yahan aap start_vm, create_new_vm functions ko use kar sakte hain)

declare -A OS_OPTIONS=(
    ["Ubuntu 24.04"]="ubuntu|noble|https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img|deup-ubuntu|deup|deup123"
)

check_dependencies
# Yahan main_menu function call hogi...
```

注释是印地语/乌尔都语，意思是"剩余逻辑按你原脚本继续"、"这里会调用 main_menu"。

**`main_menu` 函数从未定义，也从未调用。** 脚本跑完 `check_dependencies` 就退出了。
这实际上是一个代码片段，不是可运行的脚本。

`OS_OPTIONS` 里还硬编码了密码 `deup123`——虽然是示例，但建议改成随机生成。

**可用性**：❌ 骨架

### 3.4 需要什么前提

这类脚本的共同前提是宿主机有 `/dev/kvm`：

```bash
ls -l /dev/kvm
# crw-rw---- 1 root kvm 10, 232 ... /dev/kvm
```

**容器里通常没有。** 本指南实测的 proot 环境（`CapEff=0`）必然没有。
判断方法见 [examples/check-capabilities.sh](../examples/check-capabilities.sh)。

## 4. 技术路线三：Docker + Web 终端

### 4.1 Render-Vps —— gotty 方案

```dockerfile
FROM ubuntu:22.04
ENV GOTTY_TAG_VER=v1.0.1
RUN apt-get -y update && \
    apt-get install -y curl && \
    curl -sLk https://github.com/yudai/gotty/releases/download/${GOTTY_TAG_VER}/gotty_linux_amd64.tar.gz \
    | tar xzC /usr/local/bin && ...
COPY /lapio-plays.sh /lapio-plays.sh
EXPOSE 8080
CMD ["/bin/bash", "/lapio-plays.sh"]
```

gotty 把任意命令转成 Web 服务。实测该 gotty release 可用（HTTP 200）。

**但有个安全问题**：`curl -sLk` 的 `-k` 表示忽略 TLS 证书错误。下载可执行文件时
跳过证书验证，等于关掉了 MITM 防护。去掉 `-k` 更稳妥。

另外 `COPY /lapio-plays.sh` 中的 `/` 是相对于构建上下文的根，写法不规范，
虽然能工作，但容易误以为在拷宿主机的 `/`。

**可用性**：✅ 结构完整，建议去掉 `-k`

### 4.2 docker-ubuntu-desktop —— 桌面版

Ubuntu + 桌面环境 + noVNC。文件数 5，README 有说明。和 proot 方案互补：
想要图形界面时可以用。

## 5. 技术路线四：面板

### WINGS-SETUP

```bash
bash <(curl -s https://pterodactyl-installer.se) --panel
```

一行装 Pterodactyl 面板。

`bash <(curl ...)` 这个模式要谨慎：**代码直接来自第三方，你执行前看不到内容**。
如果对方服务器被入侵或域名易主，你就在跑陌生代码。

想用的话，先下载看一遍：

```bash
curl -sO https://pterodactyl-installer.se
less pterodactyl-installer
bash pterodactyl-installer --panel
```

**可用性**：⚠️ 能用，但建议先审计

## 6. 横向对比

| 维度 | proot | QEMU | Docker | 面板 |
|---|---|---|---|---|
| 真 root | ❌ | ✅ | ❌ | ✅ |
| 需要 KVM | ❌ | ✅ | ❌ | — |
| 内存开销 | 低（共享内核） | 高（完整 OS） | 中 | — |
| 启动速度 | 秒级 | 分钟级 | 秒级 | — |
| 能跑 Docker | ❌ | ✅ | 部分 | — |
| 适用场景 | 日常开发 | 需要内核特性 | 隔离服务 | 游戏服托管 |

**选择建议**：

- 只想装包、跑脚本、用 `apt` → **proot**（本指南方案）
- 需要 sysctl / iptables / 内核模块 / 嵌套 Docker → **QEMU**（前提是有 KVM）
- 要长期跑一个服务 → **Docker**
- 图形界面 → **noVNC** 类方案

## 7. 共同的坑（重点）

### 坑一：临时直链会死

```
mediafire   → 302 → download_repair.php?flag=4    失效
proot.me    → DNS 无响应                          失效
```

**规律**：凡是 `download<数字>.xxx.com`、带 `dkey`/`qkey` 参数的，都是带时效的临时链接。
文档里写这种地址等于写了个定时炸弹。

用官方稳定地址或 GitHub Release 直链。

### 坑二：`curl | bash`

```bash
bash <(curl -s https://pterodactyl-installer.se)
```

省事，但把执行权交给远端。在沙盒里试没关系，在正式机器上建议先下载审计。

### 坑三：半成品当成品

`IDX-VPS` 有印地语注释写着"剩余逻辑按你原脚本继续"，`main_menu` 从未定义。
`Make-KVM-Supported-Vps-` 的 README 只有 1 行。

看仓库的**文件数**和**代码行数**能提前判断：

```bash
find . -type f -not -path "./.git/*" | wc -l
find . -name "*.sh" -exec cat {} + | wc -l
```

20 个仓库里 4 个是纯文档、1 个仅 1 行。**star 数不代表可用性**。

### 坑四：品牌驱动的脚本

到处是 `DeUp Gaming`、`KEXSONHOST`、Discord 邀请链接。
这类脚本常夹带引流，主要目的是聚人而不是提供工具。技术上可以参考，但别当权威。

### 坑五：批量更新

21 个仓库里 **18 个** 的 `updated_at` 都是 `2026-10-02`（实际统计：10-02 共 18 个，其余
11-09 / 11-07 / 10-18 各 1 个）。这是批量操作（可能只是改 README），
不代表代码在维护。

### 坑六：挖矿

`xmrig` 是 RandomX/KawPow 挖矿程序。把它和一堆"免费 VPS 脚本"放一起，意图很明显。

**在别人的云资源上挖矿，几乎必然违反服务条款**，后果是账号封禁。本文不分析、
不建议、也不提供任何相关方法。

## 8. 对本站文档的影响

调研后，本指南 [02-快速上手](02-快速上手.md) 的建议不变：

1. **freeroot 仍是首选**——代码最干净，实测通过
2. 可以借鉴 ROOT 的两个改进：
   - `env -i` 清环境（避免宿主变量污染）
   - `-b /tmp`（按需，注意隔离性代价）
3. `bootstrap.sh` 依旧作为定制备选，支持 autodetect

**不采纳**的部分：freeroot 的 `proot` 和 rootfs 下载源都是硬编码的单点，
`bootstrap.sh` 里做了多源和校验，这比照抄 freeroot 稳。

## 附录 B：如何快速评估一个此类仓库

```bash
# 1. 看规模和真实代码量
git clone --depth 1 <url> /tmp/r && cd /tmp/r
find . -type f -not -path "./.git/*" | wc -l
find . -name "*.sh" -o -name "Dockerfile" | xargs wc -l 2>/dev/null | tail -1

# 2. 提取所有外链，批量验活
grep -rhoE 'https?://[^"'"'"' `)]+' . | sort -u | while read u; do
  printf "%-90s %s\n" "$u" "$(curl -s -o /dev/null -w '%{http_code}' -L --max-time 10 "$u")"
done

# 3. 查是否有未定义函数（半成品的标志）
grep -oE '^[a-z_]+\(\)' *.sh | cut -d: -f2 | tr -d '()' | sort -u > /tmp/defined
grep -oE '\b[a-z_]+\b(?= )' *.sh > /dev/null 2>&1 || true
# 手工核对 main() 之类是否有调用

# 4. 查提交新鲜度
git log -1 --format='%ci %s'
```
