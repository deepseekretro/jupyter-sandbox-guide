## 2. 技术路线一：proot（伪 root）

本指南采用的方案。proot 用 `ptrace` 拦截 syscall 伪造 root 身份，**共享宿主内核**，
所以轻量、秒级启动，但 `CapEff` 为 0，chroot/mount/sysctl 全不可用。

### 2.1 freeroot —— 原版，最干净

`dxdgame/freeroot` 是 fork：

```json
fork: true    parent: foxytouxxx/freeroot    license: MIT
```

我文档 [03-proot详解](03-proot详解.md) 的逐行分析就是基于它。核心三步：

```sh
ROOTFS_DIR=$(pwd)                                           # 当前目录当 rootfs
tar -xf /tmp/rootfs.tar.gz -C $ROOTFS_DIR                   # Ubuntu base 解到自己身上
wget -O $ROOTFS_DIR/usr/local/bin/proot ".../proot-x86_64"   # 静态 proot
```

启动：

```sh
$ROOTFS_DIR/usr/local/bin/proot \
  --rootfs="${ROOTFS_DIR}" \
  -0 -w "/root" -b /dev -b /sys -b /proc -b /etc/resolv.conf --kill-on-exit
```

**细节**：`wget` 有 50 次重试，每次 `timeout=1`；proot 下载后校验非空（`[ ! -s ]`）。
对一个 1.9 MB 的文件这么谨慎，说明作者遇到过网络抖动。

**可用性**：✅ 实测通过（见 [07-实战案例](07-实战案例.md)）

### 2.2 ROOT —— freeroot 的重写，两个实质改进

行数从 219 涨到 353，主要变化不是 UI，而是两处行为修正。

**改进一：多了 `-b /tmp`**

```sh
-freeroot: -b /dev -b /sys -b /proc -b /etc/resolv.conf
+ROOT:     -b /dev -b /sys -b /proc -b /tmp -b /etc/resolv.conf
```

让 guest 和 host 共享 `/tmp`。好处是编译产物可以直接交换；坏处是隔离性归零——
guest 里 `rm -rf /tmp/*` 会删宿主的文件。

**改进二：`env -i` 清洁环境**

```sh
exec "$ROOTFS_DIR/usr/local/bin/proot" ... \
  /usr/bin/env -i \
  HOME=/root \
  TERM="$TERM" \
  PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
  /bin/bash --login
```

`env -i` 清空所有继承变量，只保留三个。这避免了宿主的 `LD_PRELOAD`、`PYTHONPATH`
污染 guest。**这一条值得抄**——我们文档 [06-限制与风险](06-限制与风险.md) 提过这个问题。

**额外改进**：ROOT 会先检查依赖再下载：

```sh
install_dependencies() {
    echo -e "${CYAN}[*] Checking dependencies...${RESET}"
```

freeroot 不检查，缺 `wget`/`tar` 会直接报错。

**问题：proot 源不同，二进制也不同**

```sh
-freeroot: https://raw.githubusercontent.com/foxytouxxx/freeroot/main/proot-x86_64
+ROOT:     https://proot.gitlab.io/proot/bin/proot
```

实测两份都活着，但**大小差 77 KB**：

| 源 | 大小 | 特征 |
|---|---|---|
| freeroot | 1,901,440 B | 已 strip |
| proot.gitlab.io | 1,978,448 B | 带 debug_info，未 strip |

**两份是不同的构建，不要混用。**

**可用性**：✅ 能用（注意联网检测依赖）

### 2.3 REPLIT-24-7-VPS —— 两个 URL 都是错的

## 3. 技术路线二：QEMU 真虚拟机

和 proot 的本质区别：**QEMU 是真硬件模拟，内核自己跑**。能得到真 root，
代价是需要 `/dev/kvm`，内存翻倍。

### 3.1 idx-vps1 —— 这批里质量最高的

936 行，**19 个函数**，完整的多 VM 生命周期管理：

```
validate_input  check_dependencies  cleanup
get_vm_list     load_vm_config      save_vm_config    edit_vm_config
create_new_vm   setup_vm_image      delete_vm
start_vm        stop_vm             restart 相关
show_vm_info    show_vm_performance is_vm_running     resize_vm_disk
display_header  print_status        main_menu
```

**数据模型**：每个 VM 一个 `.conf` 文件存配置，`save_vm_config`/`load_vm_config`
读写，`get_vm_list` 枚举。这是正经的设计，不是一次性脚本。

**cloud-init 集成**：

```bash
cat > user-data <<EOF
#cloud-config
hostname: $HOSTNAME
ssh_pwauth: true
disable_root: false
users:
  - name: $USERNAME
    sudo: ALL=(ALL) NOPASSWD:ALL
    shell: /bin/bash
    password: $(openssl passwd -6 "$PASSWORD" | tr -d '\n')
chpasswd:
  list: |
    root:$PASSWORD
    $USERNAME:$PASSWORD
  expire: false
EOF
cloud-localds "$SEED_FILE" user-data meta-data
```

密码用 `openssl passwd -6` 生成 SHA-512 哈希，没明文落盘。**做法正确。**

**QEMU 参数也很专业**：

```bash
qemu-system-x86_64 -enable-kvm -m "$MEMORY" -smp "$CPUS" -cpu host \
  -drive "file=$IMG_FILE,format=qcow2,if=virtio" \
  -drive "file=$SEED_FILE,format=raw,if=virtio" \
  -device virtio-net-pci,netdev=n0 \
  -netdev "user,id=n0,hostfwd=tcp::$SSH_PORT-:22" \
  -device virtio-balloon-pci \
  -object rng-random,filename=/dev/urandom,id=rng0 \
  -device virtio-rng-pci,rng=rng0
```

virtio 全套（磁盘/网络/气球/随机数）、`-cpu host` 透传、熵源注入——这是有经验的人写的。
`virtio-rng` 尤其到位，虚拟机常见的启动卡顿就是熵不足。

**但有三个真实缺陷：**

**缺陷 1：README 的安装命令是错的**

```bash
bash <(curl -fsSL https://github.com/dxdgame/idx-vps1/blob/main/vps.sh)
```

实测这个 URL 返回 **HTTP 200 但内容是 HTML**：

```
$ curl -sL .../blob/main/vps.sh | head -c 80
<!DOCTYPE html>
<html lang="en" data-color-mode="auto" data-light...
```

`blob/main` 是 GitHub 的网页视图。`bash <(curl ...)` 会拿到一整个 HTML 页面喂给 bash，
结果是满屏语法错误。**正确写法是 `raw.githubusercontent.com`**：

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/dxdgame/idx-vps1/main/vps.sh)
```

**缺陷 2：resize 失败后的分支逻辑自相矛盾**

```bash
if ! qemu-img resize "$IMG_FILE" "$DISK_SIZE" 2>/dev/null; then
    rm -f "$IMG_FILE"                                              # ← 先删了
    qemu-img create -f qcow2 -F qcow2 -b "$IMG_FILE" "$IMG_FILE.tmp" "$DISK_SIZE"
    #                                      ↑ 又拿它当 backing file
```

`rm -f` 之后又用 `-b "$IMG_FILE"` 引用同一个文件作后端。文件已删，这必然失败
（靠 `||` 回退到 `qemu-img create` 才没崩）。正确顺序应该是先 create 后删，或者用临时变量。

**缺陷 3：端口转发的网卡 id 会重复**

```bash
qemu_cmd+=(-device "virtio-net-pci,netdev=n${#qemu_cmd[@]}")
qemu_cmd+=(-netdev "user,id=n${#qemu_cmd[@]},hostfwd=tcp::$host_port-:$guest_port")
```

用数组长度当 id 后缀。但每次 `+=` 两个元素，长度递增 2，两次循环拿到的是 `n24` 和 `n26`
（不冲突但其实也没意义），更糟的是**两个 `+=` 之间长度已经变了**——`-device` 用的
是当时的长度，`-netdev` 用的是加 1 之后的长度，**同一轮里两个 id 就不一致**。

`id=nX` 和 `netdev=nX` 必须相等才能配对。这里必然错位。

**可用性**：✅ 主体可用，但安装命令必须换成 raw 地址；多端口转发会失败

**缺陷 4：7 个发行版镜像里有 1 个已 404**

`OS_OPTIONS` 里预设了 7 个发行版。实测结果：

| 发行版 | 状态 |
|---|---|
| Debian 12 (bookworm) | ✅ 200 |
| Debian 11 (bullseye) | ✅ 200 |
| Rocky Linux 9 | ✅ 200 |
| AlmaLinux 9 | ✅ 200 |
| CentOS Stream 9 | ✅ 200 |
| Ubuntu jammy / noble | ⚠️ 需强制 DNS（见附录 A.3） |
| **Fedora 40** | ❌ **404**（跳 CloudFront 后 404，release 40 已下架） |

```bash
# 实测
curl -sIL https://download.fedoraproject.org/pub/fedora/linux/releases/40/Cloud/x86_64/images/Fedora-Cloud-Base-40-1.14.x86_64.qcow2
# HTTP/2 302
# location: https://d2lzkl7pfhq30w.cloudfront.net/pub/fedora/...
# HTTP/2 404
```

Fedora 的 release 下架很快，硬编码具体版本号（`40-1.14`）必然过期。
应改用 `releases/40/Cloud/x86_64/images/Fedora-Cloud-Base-40-*.qcow2` 通配（需先列目录）。

### 3.3 IDX-VPS —— 确认是骨架

90 行，只定义了 3 个函数（`check_dependencies` / `display_header` / `print_status`），
全是工具函数，**没有一个业务函数**。

```bash
# [Baqi logic aapke original script ke mutabiq continue rahega...]
# (Yahan aap start_vm, create_new_vm functions ko use kar sakte hain)

declare -A OS_OPTIONS=(
    ["Ubuntu 24.04"]="ubuntu|noble|...|deup-ubuntu|deup|deup123"
)

check_dependencies
# Yahan main_menu function call hogi...
```

注释是印地语/乌尔都语，直译："剩余逻辑按你原脚本继续"、"这里会调用 main_menu"。

**`main_menu` 从未定义，也从未调用。** 脚本跑完 `check_dependencies` 就退出了。
这是代码片段，不是可运行的脚本。

另外 `OS_OPTIONS` 里硬编码密码 `deup123`，虽然是示例，但理念不好。

对比 `idx-vps1`：同名项目，一个 936 行 19 函数，一个 90 行 3 函数。
**同一个作者的水平差异说明了 star 数与可用性无关**。

**可用性**：❌ 骨架

### 3.4 DAYTONA-VPS1 —— 有亮点，也有风险

275 行，9 个函数（`boot_qemu` / `create_vps` / `configure_tcp` / `restart_vps` /
`save_env` / `clean_vps` / `show_menu` / `loading_bar` / `type_effect`）。

**亮点：用 sshx 解决"容器里怎么访问"的问题**

```bash
sshx_log=$(mktemp)
curl -sSf https://sshx.io/get | sh -s run > "$sshx_log" 2>&1 &
sleep 5
SSHX_URL=$(grep -o 'https://sshx.io/s/[a-zA-Z0-9]*' "$sshx_log" | head -n 1)
```

`sshx` 是一个把终端转成 Web 链接的工具，不需要公网 IP 或端口映射。
实测 `https://sshx.io/get` 返回真实脚本（`#!/bin/sh`）。

这解决了一个真问题：**免费容器平台通常不给入站端口**，常规 SSH 连不上。
用出站连接换一个临时 web 链接，思路是对的。

**但风险明显**：

1. `sleep 5` 硬编码等 URL 出现，慢一点就抓不到
2. 链接是**临时的、公开的**——任何拿到 URL 的人都能进终端
3. 默认口令 `1234`（`${USER_PASS:-1234}`）
4. `curl | sh` 直接执行远端脚本

**可用性**：⚠️ 能跑，但安全上要自己加措施

### 3.5 共同前提：`/dev/kvm`

QEMU 方案全部要求宿主暴露 KVM：

```bash
ls -l /dev/kvm
# crw-rw---- 1 root kvm 10, 232 ... /dev/kvm
```

**容器里通常没有。** 本指南实测的 proot 环境（`CapEff=0`）必然没有。
判断方法见 [examples/check-capabilities.sh](../examples/check-capabilities.sh)。

没有 KVM 时的报错：

```
qemu-system-x86_64: -enable-kvm: KVM not available: /dev/kvm: No such file or directory
```

`idx-vps1` 的 `check_dependencies` 只查命令存在性，**不查 `/dev/kvm`**——
这是它一个疏漏，装上 QEMU 后发现跑不起来会更困惑。

## 4. 技术路线三：Docker + Web 终端

### 4.1 Render-Vps —— gotty 方案

```dockerfile
FROM ubuntu:22.04
ENV GOTTY_TAG_VER=v1.0.1
RUN apt-get -y update && apt-get install -y curl && \
    curl -sLk https://github.com/yudai/gotty/releases/download/${GOTTY_TAG_VER}/gotty_linux_amd64.tar.gz \
      | tar xzC /usr/local/bin && \
    apt-get purge --auto-remove -y curl && \
    apt-get clean && rm -rf /var/lib/apt/lists/*
COPY /lapio-plays.sh /lapio-plays.sh
EXPOSE 8080
CMD ["/bin/bash", "/lapio-plays.sh"]
```

gotty 把任意命令转成 Web 服务。实测该 release 可用（HTTP 200）。

**写得对的地方**：安装完立刻 `apt-get purge --auto-remove -y curl` 并清 apt 缓存，
减小镜像。这是良好实践。

**问题一：`curl -sLk` 的 `-k`**

跳过 TLS 证书验证。下载可执行文件时关掉 MITM 防护，不适合。去掉 `-k` 即可。

**问题二：`COPY /lapio-plays.sh`**

`/` 在这里是构建上下文的根，不是宿主机根。能工作但容易误导。

**可用性**：✅ 结构完整，建议去掉 `-k`

### 4.2 FREE-VPS-5 / VPSUbuntuHF —— Hugging Face Spaces 方案

两个仓库的 README **内容几乎一致**（都 135 行），讲的是同一个套路：

```dockerfile
FROM ubuntu:24.04
ENV DEBIAN_FRONTEND=noninteractive
RUN apt-get update && apt-get install -y curl sudo git wget build-essential python3 python3-pip \
    && rm -rf /var/lib/apt/lists/*
RUN curl -fsSL https://code-server.dev/install.sh | sh
RUN echo "ubuntu ALL=(ALL) NOPASSWD:ALL" >> /etc/sudoers
USER ubuntu
EXPOSE 7860
```

**技术要点**：`7860` 是 Hugging Face Spaces 的固定端口。用 `code-server`
（浏览器版 VS Code）提供 Web IDE，密码走 Spaces 的 Secret 注入。

**配套的保活手段**：README 要求注册 cron-job.org 定时 ping，防止 Space 休眠。
这是免费 PaaS 的通用问题——闲置即回收。

**评价**：这套是真能用的（HF Spaces 稳定、有免费额度），但：

- 本质是**用 Spaces 当开发机**，不是 VPS，无 root、无入站端口
- 需要账号 + 定期 ping，属于"薅羊毛"性质，随时可能被平台改规则
- 两个仓库内容重复，说明是复制粘贴维护的

**可用性**：✅ 能跑，但要看平台政策

### CodeSandBox-and-ptero-setup

唯一带**免责声明**的仓库，值得肯定：

> **Disclaimer:** This guide is for educational purposes. CodeSandbox is a cloud
> development environment and does not officially provide a permanent VPS.
> Availability depends on CodeSandbox's policies.

这是 21 个仓库里唯一明确承认「平台不保证可用性」的。**态度是对的。**

但它调的 `ptero.nobitahost.in` 是个人域名（实测返回脚本，内容是
"NOBITA CLOUD SYSTEM | BANE-ANMESH 1S UPLINK"），可信度低于官方 installer。

## 6. 横向对比

| 维度 | proot | QEMU | Docker | 面板 |
|---|---|---|---|---|
| 真 root | ❌ | ✅ | ❌ | ✅ |
| 需要 KVM | ❌ | ✅ | ❌ | — |
| 内存开销 | 低（共享内核） | 高（完整 OS） | 中 | — |
| 启动速度 | 秒级 | 分钟级 | 秒级 | — |
| 能跑 Docker | ❌ | ✅ | ❌ | — |
| 能改 sysctl | ❌ | ✅ | ❌ | — |
| 入站端口 | 需隧道 | 需 hostfwd | 平台定 | 平台定 |
| 适用场景 | 日常开发 | 内核级需求 | 隔离服务 | 游戏服 |

**选择建议**：

- 装包、跑脚本、`apt install` → **proot**（本指南方案，最省事）
- 需要 sysctl / iptables / 内核模块 / 嵌套 Docker → **QEMU**（前提：有 `/dev/kvm`）
- 长期跑一个服务 → **Docker**
- 要图形界面 → **noVNC** 类方案

## 7. 六个共性坑

### 坑一：临时直链会死

```
mediafire         302 → download_repair.php?flag=4   失效
proot.me          DNS 无响应                          失效
proot-distro      404                                文件名不对
Fedora 40         302 → CloudFront → 404              release 已下架
```

**识别规律**：

- 域名形如 `download<数字>.xxx.com`
- URL 带 `dkey` / `qkey` / `token` 参数
- 跳转到 `*_repair.php`、`*_error.php`
- 硬编码了具体版本号（`40-1.14`），而不是 `latest`

**特别提醒**：这类链接 **HEAD 请求可能返回 200**，但拿到的是失效页面本身。
判断**必须跟 302**（`curl -L`）或看 `content-type`：

```bash
# 不够
curl -s -o /dev/null -w '%{http_code}' "$url"

# 够（跟跳转）
curl -sL -o /dev/null -w '%{http_code}' --max-time 10 "$url"
```

媒体火那个链接就是典型：不跟跳转是 200，跟了才暴露问题。

### 坑二：`blob` 不是 `raw`

```bash
# 错：拿到 HTML
bash <(curl -fsSL https://github.com/user/repo/blob/main/script.sh)

# 对：拿到脚本
bash <(curl -fsSL https://raw.githubusercontent.com/user/repo/main/script.sh)
```

实测 `blob/main` 返回 `<!DOCTYPE html>`。整个 HTML 喂给 bash，满屏语法错误。

**这个坑非常常见**，21 个仓库里就有一个踩了（`idx-vps1`）。

### 坑三：`curl | bash`

```bash
bash <(curl -s https://pterodactyl-installer.se)
curl -sSf https://sshx.io/get | sh -s run
curl -fsSL https://code-server.dev/install.sh | sh
```

省事，但把执行权交给远端。沙盒里试无所谓，正式机器建议先下载审计。

### 坑四：半成品当成品

`IDX-VPS` 有印地语注释"剩余逻辑按你原脚本继续"，`main_menu` 从未定义。
`Make-KVM-Supported-Vps-` 的 README 只有 1 行。

**快速判断法**：

```bash
# 1. 真实代码量
find . -name "*.sh" -not -path "./.git/*" -exec cat {} + | wc -l

# 2. 定义了哪些函数
grep -oE '^[a-z_]+\(\)' *.sh | tr -d '()'

# 3. 末尾有没有真正调用主函数
tail -5 *.sh
```

`IDX-VPS` 定义 3 个函数（全是工具函数）、末尾只调 `check_dependencies` → 骨架。
`idx-vps1` 定义 19 个函数、末尾调 `main_menu` → 完整。

### 坑五：品牌驱动的脚本

到处是 `DeUp Gaming`、`KEXSONHOST`、Discord 邀请链接、`deup123` 这种占位密码。
这类脚本常有引流目的，主要目标是聚人而非提供工具。

技术上可以参考（`idx-vps1` 的 cloud-init 就写得不错），但别当权威。

### 坑六：批量更新 ≠ 在维护

实测 `updated_at` 分布：

```
2026-10-02   18 个    ← 一天批量动了 18 个
2026-11-09    1 个
2026-11-07    1 个
2026-10-18    1 个
```

18 个仓库同一天更新，大概率是批量改 README 或加文件。
**看 `pushed_at` 比 `updated_at` 更准**：

```bash
git log -1 --format='%ci %s'
```

### 附：挖矿

`xmrig` 是 RandomX/KawPow 挖矿程序。和一整排"免费 VPS 脚本"放一起，意图明显。

**在他人云资源上挖矿几乎必然违反服务条款**，后果是封号。本文不分析、不建议、
不提供任何方法。这一项我直接跳过了。

## 8. 对本站文档的影响

调研后本指南的建议**不变**，但有三处可以吸收：

**采纳 1：`env -i` 清环境**（来自 ROOT）

避免宿主 `LD_PRELOAD`、`PYTHONPATH` 污染 guest。这是实质改进。

**采纳 2：先检查依赖再下载**（来自 ROOT）

freeroot 不检查，缺 `wget` 会报难懂的错。`bootstrap.sh` 已有检查。

**不采纳：硬编码下载源**

freeroot 的 proot 和 rootfs 都是单点 URL。`bootstrap.sh` 做了多源和校验，更稳。

**不采纳：`-b /tmp`**

隔离性代价太大。需要传文件时显式 `cp` 更安全。

**待验证**：`cdimage.ubuntu.com` 在测试环境 DNS 解析失败，但**站点本身是活的**——
用 `--resolve` 强制指定 IP 后返回 200，下载的 tarball 魔数 `1f 8b` 正确，能解出 348 个条目
（`bin`/`boot/`/`dev/`/`etc/`）。因此 [02-快速上手](02-快速上手.md) 中的地址**可用**，
只是某些环境解析不了这个子域。详见附录 A。

**关于版本的发现（有实际意义）**：两个 release 目录的索引不一致。

| 目录 | 实际列出 | freeroot/ROOT 硬编码的 |
|---|---|---|
| `20.04/release/` | 只列 **20.04.1** | freeroot 用 **20.04.4** |

ROOT 的 22.04.5 稳。如果你在改 freeroot，建议把版本换成目录里明确列出的那个。

## 附录 B：仓库快速评估脚本

```bash
#!/bin/bash
# 用法: ./assess.sh <github-url>
set -uo pipefail
tmp=$(mktemp -d)
git clone --depth 1 -q "$1" "$tmp/r" 2>/dev/null || { echo "克隆失败"; exit 1; }
cd "$tmp/r"

echo "=== 规模 ==="
echo "文件数: $(find . -type f -not -path './.git/*' | wc -l)"
echo "代码行: $(find . -type f \( -name '*.sh' -o -name 'Dockerfile*' \) -not -path './.git/*' -exec cat {} + 2>/dev/null | wc -l)"

echo "=== 函数完整性 ==="
for f in *.sh; do
  [ -f "$f" ] || continue
  echo "$f: $(grep -coE '^[a-z_][a-z0-9_]*\(\)' "$f") 个函数定义"
  echo "  末尾: $(tail -2 "$f" | tr '\n' ' ')"
done

echo "=== 外链验活 ==="
# 注意正则：要排除 | 和空格，否则会把 OS_OPTIONS 的整行当 URL
grep -rhoE 'https?://[^"'"'"'` )|]+' . 2>/dev/null | sed 's/[.,;:]$//' | sort -u | while read -r u; do
  code=$(curl -s -o /dev/null -w '%{http_code}' -L --max-time 10 "$u" 2>/dev/null)
  printf "  %-3s %s\n" "$code" "$u"
done

echo "=== 常见错误 ==="
grep -rn "blob/main\|blob/master" --include="*.sh" --include="*.md" . 2>/dev/null | grep -v '^./.git'
grep -rnE "password[=:]\s*['\"][^'\"\$]{3,}" --include="*.sh" . 2>/dev/null | grep -v '^./.git'

echo "=== 提交新鲜度 ==="
git log -1 --format='%ci  %s'

cd / && rm -rf "$tmp"
```

实测可跑，5 秒出结果。附录 A 的结论就是这个脚本跑出来的。

**注意正则里的 `|`**：`idx-vps1` 把镜像地址写在 `declare -A OS_OPTIONS` 里，
格式是 `"name|ver|url|user|pass|pass"`。如果正则不排除 `|`，会把整行当一个 URL，
得到假 404。这是实测踩到的。
