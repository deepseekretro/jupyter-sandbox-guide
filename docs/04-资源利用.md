# 04 — 资源利用

如何压榨沙盒的 CPU / 内存 / 磁盘，跑长时间任务而不被杀。

---

## 内存

### 先看清真相

```bash
free -g
#               total   used   free  shared  buff/cache  available
# Mem:            21     14      1     0        5           6
```

**不要只看 `free`！** `used` 包含了 `buff/cache`（可回收）。真正能用的是 `available`。

更准的指标是 cgroup：

```bash
# cgroup v2
cat /sys/fs/cgroup/memory.current     # 当前用量
cat /sys/fs/cgroup/memory.max         # 上限（可能是假的）
cat /sys/fs/cgroup/memory.stat        # 明细

# cgroup v1
cat /sys/fs/cgroup/memory/memory.usage_in_bytes
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
```

### 拆解 memory.stat

```
anon        1837 MB   ← 进程真实堆内存（这个才重要）
file        2780 MB   ← 页缓存（可回收）
kernel       175 MB   ← 内核对象
slab         140 MB   ← 内核 slab
sock          12 MB
```

**判断内存压力看 `anon`，不是 `used`。**

### 揭露真实上限

cgroup 显示 `max` 不代表无限制（**可能是宿主外层限制，容器内根本看不到**）。

实测方法 —— 逐页写入，看什么时候被 SIGKILL：

```bash
python3 - <<'EOF'
import sys
CHUNK = 256 * 1024 * 1024          # 256 MB
kept = []
try:
    for i in range(1, 100):
        b = bytearray(CHUNK)
        for off in range(0, len(b), 4096):   # 逐页触碰，确保真实分配
            b[off] = 1
        kept.append(b)
        print(f"{i*256} MB  OK", flush=True)
except MemoryError:
    print("MemoryError at", len(kept)*256, "MB")
EOF
echo "exit=$?"      # 137 = SIGKILL（被 OOM killer 杀掉）
```

如果输出在某个值突然中断、`exit=137` → **那就是真实上限**。

> 血泪教训：曾有机器 cgroup 显示 `max`，Python `mmap` 8 GB 也正常，
> 但实际跑大程序在 5 GB 就被杀。OOM 是**物理页分配**时才触发，
> `mmap` 只是地址空间预留，骗不过。

### 无 swap 的后果

```bash
swapon --show     # 空输出 = 无 swap
```

**无 swap 意味着 OOM 直接 SIGKILL，没有任何缓冲。**

后果：
- 程序不会"变慢"，会**突然消失**
- `dmesg | tail` 能看到 `Killed process`
- 长期任务必须自己限制内存

### 限制内存的方法

```bash
# 1. ulimit（软限制，程序超了会 malloc 失败而非被杀）
ulimit -v 4000000        # 4 GB 虚拟内存

# 2. cgroup（如果可写）
echo "4G" > /sys/fs/cgroup/mygroup/memory.max

# 3. 程序自带参数
java -Xmx6G ...          # JVM
python -c "... "         # 手动分块

# 4. systemd-run（如果有 systemd）
systemd-run --scope -p MemoryMax=4G ./task
```

**最实用的：JVM / 编译器 / 数据库都自带内存参数，直接用。**

| 软件 | 参数 |
|---|---|
| Java | `-Xmx4G -Xms1G` |
| GCC | `-j2`（并行度影响内存） |
| Go | `GOGC=50`（降低 GC 阈值） |
| Node | `--max-old-space-size=4096` |
| Redis | `maxmemory 4gb` |

### Java 堆设置的坑

```bash
# ❌ 错误：设了 -Xmx 但容器也被占满
java -Xmx16G -jar app.jar    # 容器只有 8 GB → 必死

# ✅ 正确：留余量给堆外内存
# 经验法则：-Xmx = 可用内存 × 0.7
java -Xmx6G -jar app.jar
```

堆外内存包括：
- JVM 自身（元空间、代码缓存）
- DirectByteBuffer（NIO）
- 线程栈
- GC 结构（G1 的 remembered set）

**Ghidra 实测建议**：

| 目标文件大小 | `-Xmx` |
|---|---|
| < 10 MB | 默认（约 2G） |
| 10–100 MB | `-Xmx6G` |
| > 100 MB | `-Xmx8G`（无 swap 时的上限） |

## CPU

### 看清真实核数

```bash
nproc                          # 可用核数
grep -c ^processor /proc/cpuinfo   # 物理核数
lscpu | grep -E "^CPU\(s\)|Thread|Core|Socket"
```

**注意**：`nproc` 可能受 cgroup `cpu.max` 限制，`/proc/cpuinfo` 显示的是宿主全部。

### 别把机器打满

**关键教训**：跑满所有核 → **sshd 抢不到 CPU → SSH 彻底失联**。

```bash
# ❌ 危险：4 核全占
make -j$(nproc)

# ✅ 安全：留 1 核给系统
make -j$(( $(nproc) - 1 ))
```

更保守的公式：

```bash
JOBS=$(( $(nproc) * 3 / 4 ))
[ $JOBS -lt 1 ] && JOBS=1
make -j$JOBS
```

### 用 nice 降低优先级

```bash
nice -n 19 ./heavy_task          # 最低优先级
ionice -c 3 ./heavy_task         # 最低 I/O 优先级
```

### 限制特定进程

```bash
# CPU 亲和性（绑定到 2 个核）
taskset -c 0,1 ./task

# cgroup cpu 限制
echo "200000 100000" > /sys/fs/cgroup/mygroup/cpu.max  # 限 2 核
```

**Java/Ghidra 的 `-max-cpu` 就是这么实现的**：

```bash
analyzeHeadless ... -max-cpu 2
```

## 磁盘

### 看清用量

```bash
df -h /
du -sh /var/cache/apt /tmp /root 2>/dev/null
```

### 大杀器：编译缓存

编译产生的缓存能吃几个 GB：

```bash
# Go
du -sh ~/.cache/go-build      # 实测 4.7 GB
go clean -cache

# pip
du -sh ~/.cache/pip
pip cache purge

# node
du -sh ~/.cache/node-gyp ~/.npm
npm cache clean --force

# apt
apt-get clean
```

### /tmp 的陷阱

```bash
df -h /tmp
# 如果和 / 同一个分区 → /tmp 不是 tmpfs，重启不丢
# 如果是 tmpfs → 占用内存！写大文件会 OOM
```

**实测案例**：某机器 `/tmp` 和 `/` 同为 overlay（135G），不是 tmpfs —— 所以能放大文件。
但 `/dev/shm` 只有 64 MB 且 `noexec`。

```bash
# 检查
findmnt /tmp /dev/shm
```

**不要假设 `/tmp` 是 tmpfs**，也不要假设它是持久的（容器重建照样丢）。

### 找空间大户

```bash
# 前 20 大目录
du -ahx / 2>/dev/null | sort -rh | head -20

# 前 20 大文件
find / -xdev -type f -size +100M 2>/dev/null \
  -printf '%s\t%p\n' | sort -rn | head -20

# 已被删除但仍占空间的文件
lsof +L1 2>/dev/null | head
```

## 长时间任务

### 三层保活

```bash
# 第 1 层：nohup（忽略 SIGHUP）
# 第 2 层：setsid（新会话，脱离终端）
# 第 3 层：&（后台）
setsid nohup ./task > /tmp/task.log 2>&1 < /dev/null &
```

**为什么要三层**：
- `nohup` 挡住 SIGHUP（终端关闭）
- `setsid` 创建新会话，进程组脱离
- `< /dev/null` 防止因 stdin 关闭而阻塞

### 用 tmux / screen（更可靠）

```bash
# 装
apt-get install -y tmux

# 新建会话
tmux new -s work

# 在会话里跑任务
./long_task

# 脱离：Ctrl+B 然后 D

# 重连
tmux attach -t work

# 列表
tmux ls
```

**tmux 优于 nohup**：能重新接管交互、看实时输出、多窗口。

### 监控脚本

```bash
# 每 30 秒记录一次资源和进度
while :; do
  echo "$(date +%F' '%T) anon=$(awk '/^anon /{printf "%.0f", $2/1048576}' /sys/fs/cgroup/memory.stat)MB load=$(cut -d' ' -f1 /proc/loadavg)"
  sleep 30
done > /tmp/monitor.log 2>&1 &
```

### 处理 OOM

```bash
# 看是否被 OOM 杀
dmesg | grep -i "killed process" | tail -5
# 或
journalctl -k | grep -i oom | tail -5
```

**应对**：
1. 降低并行度
2. 减小堆/缓存大小
3. 分块处理数据
4. 换更省内存的算法

## 网络

### 测速

```bash
# 下行
timeout 15 curl -o /dev/null -w "%{speed_download} B/s\n" \
  http://speedtest.tele2.net/100MB.zip

# 上行
dd if=/dev/zero bs=1M count=50 2>/dev/null | \
  timeout 30 curl -o /dev/null -w "%{speed_upload} B/s\n" \
  -T - http://speedtest.tele2.net/upload.php
```

### 大文件下载策略

**核心原则：能在目标机直连下载，就不要中转。**

| 方式 | 实测速度 | 说明 |
|---|---|---|
| 目标机直接 `curl` | 100%（基线） | ✅ 首选 |
| 经 SSH 隧道 `cat` 管道 | **慢一个数量级** | 只在无下载源时用 |

**实测案例**：Ghidra 544 MB
- 直连下载：约 3 分钟
- 经隧道中转：15 分钟才到 13%

而且隧道方式**传输量翻倍**（先下到 A，再从 A 传到 B）。

### 断点续传

```bash
# curl
curl -C - -o file.tar.gz https://example.com/file.tar.gz

# wget
wget -c https://example.com/file.tar.gz

# rsync（需要 ssh 且远端支持）
rsync -avP user@host:/path/file .
```

### 并行下载

```bash
# aria2c（多线程，墙裂推荐）
apt-get install -y aria2
aria2c -x 16 -s 16 -o file.tar.gz https://example.com/file.tar.gz
```

## 小结

| 维度 | 要点 |
|---|---|
| 内存 | 看 `anon` 不看 `used`；无 swap 直接杀；实测上限 |
| CPU | 留 1 核给系统，否则 SSH 失联 |
| 磁盘 | 编译缓存是最大杀手；`/tmp` 不一定是 tmpfs |
| 长任务 | `setsid nohup ... < /dev/null &` 或用 tmux |
| 网络 | 能在目标机直连就别中转 |
