## 案例 1：在 22 GB 内存沙盒上跑 Ghidra 逆向

### 背景

目标：分析一个 **52 MB 的 Windows 二进制**（`dzh2.exe`，PE32+ x86-64，未加壳）。
需求：Ghidra 完整分析，导出函数表、字符串、调用关系。

### 前一次失败（5 GB 容器）

```
容器内存硬顶 ≈ 5 GB
Ghidra 完整分析需 >5 GB（120,323 个函数）
结果：exit=137 (OOM)，被杀 22 次
```

**排除了三个嫌疑**：

| 假设 | 实测 | 结论 |
|---|---|---|
| G1GC 问题 | 换 SerialGC/ParallelGC 也死 | ✘ |
| Seccomp 限制内存 | Python mmap 8 GB 正常 | ✘ |
| cgroup 显式限制 | 全部显示 `max` | ✘（假象） |

**真相**：宿主层限制，容器内看不到。`memory.peak` 始终卡在 **5018 MB**。

**附带事故**：6 路并行把 CPU 打满 → **sshd 抢不到 CPU → SSH 彻底失联**。

### 成功的做法

```bash
# 环境
export JAVA_HOME=/opt/jdk-25.0.5+8

# 分析（关键参数：-max-cpu 2 留余量给 sshd）
/opt/ghidra_12.2_PUBLIC/support/analyzeHeadless \
  /root/dzh-proj DzhProj \
  -import /root/dzh-extract/app/dzh2.exe \
  -overwrite \
  -scriptPath /root/dzh-out \
  -postScript Export.java \
  -max-cpu 2
```

**内存曲线**（实测）：

| 时间 | anon |
|---|---|
| 40 秒 | 1054 MB |
| 3 分 | 1823 MB |
| 5 分 | 2089 MB |
| 7 分 | 2276 MB |
| 11 分 | 3729 MB |
| 14 分 | 2843 MB（GC 后回落） |

**观察**：稳步上升 + GC 会回收，没有失控。22 GB 容器完全撑得住。

### 导出脚本 Export.java

```java
import ghidra.app.script.GhidraScript;
import ghidra.program.model.listing.*;
import java.io.*;

public class Export extends GhidraScript {
    public void run() throws Exception {
        String out = System.getenv("DZH_OUT");
        if (out == null) out = "/root/dzh-out";
        new File(out).mkdirs();

        // 函数表
        FunctionManager fm = currentProgram.getFunctionManager();
        PrintWriter fw = new PrintWriter(new FileWriter(out + "/functions.txt"));
        int n = 0;
        for (Function f : fm.getFunctions(true)) {
            fw.println(f.getEntryPoint() + "\t" + f.getName()
                     + "\t" + f.getBody().getNumAddresses());
            n++;
        }
        fw.close();
        println("FUNCS=" + n);

        // 字符串
        PrintWriter sw = new PrintWriter(new FileWriter(out + "/strings.txt"));
        int sc = 0;
        for (Data d : currentProgram.getListing().getDefinedData(true)) {
            if (d.getValue() instanceof String) {
                String v = (String) d.getValue();
                if (v.length() >= 4) {
                    sw.println(d.getAddress() + "\t" + v.replace("\n", "\\n"));
                    sc++;
                }
            }
        }
        sw.close();
        println("STRINGS=" + sc);
    }
}
```

### 备用方案：分阶段法

如果内存真的不够，用这个（在 5 GB 容器上验证过）：

```
1. -noanalysis 仅导入              → 940 MB
2. GhidraScript 定向扫描 .rdata     → 定位目标数据块
3. 纯 Python 解码                   → 不占 JVM 内存
```

**成果**：还原出 **19/19 个 protobuf schema**（225 消息 / 1222 字段）。

**关键洞察**：**不是所有分析都需要完整反编译。** 很多数据（协议定义、配置、密钥）就以明文或半结构化形式躺在数据段里，直接提取比反编译高效得多。

## 案例 2：在 proot 里装 SSH 服务端

### 需求

沙盒需要通过 SSH 远程接入（做长时间任务、传文件）。

### 失败：OpenSSH

```bash
apt-get install -y openssh-server
/usr/sbin/sshd
```
客户端连接：
```
$ ssh -p 2222 root@host
Connection reset by peer
```

服务端日志：
```
sshd[1234]: fatal: chroot("/var/empty"): Operation not permitted
```

**根因**：OpenSSH 的 privsep 机制要 `chroot` 到 `/var/empty`，proot 里没有 `CAP_SYS_CHROOT`。

### 成功：dropbear

dropbear 不做 privsep chroot：

```bash
cd /tmp
curl -L -o dropbear.tar.bz2 https://matt.ucc.asn.au/dropbear/releases/dropbear-2022.83.tar.bz2
tar xjf dropbear.tar.bz2
cd dropbear-2022.83

# 关掉不需要的特性（减少依赖）
./configure --prefix=/opt/dropbear \
  --disable-zlib --disable-wtmp --disable-lastlog --disable-utmpx
make -j3
make install

# host key
mkdir -p /etc/dropbear
/opt/dropbear/bin/dropbearkey -t ed25519 -f /etc/dropbear/dropbear_ed25519_host_key

# 启动
mkdir -p /var/run
/opt/dropbear/sbin/dropbear -p 22 -r /etc/dropbear/dropbear_ed25519_host_key

# 验证
ss -lntp | grep 22
```

**结果**：✅ SSH 连接正常

### 坑：dropbear 没有 sftp-server

```bash
$ scp file.tar.gz root@host:/tmp/
subsystem request failed  # ❌
```

**替代方案**：

```bash
# 用 cat 管道
cat file.tar.gz | ssh root@host 'cat > /tmp/file.tar.gz'

# 校验
sha256sum file.tar.gz
ssh root@host 'sha256sum /tmp/file.tar.gz'
```

**缺点**：无进度、无断点续传、可能因 SSH 超时中断。

**缓解**：
```bash
ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=6 ...
```

## 案例 3：解 Inno Setup 安装包

### 需求

从 `365(64).exe`（248 MB，Inno Setup 6.1.0）里提出主程序 `dzh2.exe`。

### 三次尝试

#### ❌ 尝试 1：`7z x`

```bash
7z x -y 365_64.exe
```

结果：解出 32 个文件（安装器自身的 PE 结构）：

```
.data  .text  .rsrc  CERTIFICATE  [0]
```

`[0]` 是 **258 MB 的 LZMA 压缩流**，`7z` 无法继续解压：

```
$ 7z l "[0]"
ERROR: Can not open the file as archive
```

#### ❌ 尝试 2：`innoextract 1.8`（Ubuntu 20.04 apt 版）

```bash
apt-get install -y innoextract   # 得到 1.8
innoextract -e -d out 365_64.exe
```

报错：

```
detected setup version: 6.1.0 (unicode)
error reason: basic_ios::clear: iostream error
```

**原因**：1.8 **只支持到 Inno Setup 6.0.2**。

#### ❌ 尝试 3：缺 `-s` 参数

```bash
innoextract -e -d out 365_64.exe    # 忘了 -s
```

同样崩溃。

#### ✅ 成功：`innoextract 1.9` + `-e -s`

```bash
cd /opt
curl -sL -o innoextract-1.9.tar.xz \
  https://github.com/dscharrer/innoextract/releases/download/1.9/innoextract-1.9-linux.tar.xz
tar xJf innoextract-1.9.tar.xz

/opt/innoextract-1.9-linux/bin/amd64/innoextract \
  -e -s -d /root/dzh-extract /root/365_64.exe
```

**结果**：825 MB / 16,646 文件，主程序 `app/dzh2.exe` 52 MB。

### 关键认知

| 认知 | 说明 |
|---|---|
| `-s` 不是"列表" | 是跳过 header 校验，6.1.0 必需 |
| 版本声明不可信 | 1.9 自称支持到 6.0.5，实际能解 6.1.0 |
| apt 版本可能太旧 | Ubuntu 20.04 的 apt 只有 1.8 |
| 别自己拼参数 | **先看历史/文档里验证过的完整命令** |

> **教训**：我因为没查原始命令，在这上面浪费了 3 轮尝试。

## 案例 4：跨机器传输的策略选择

### 需求

把 544 MB 的 Ghidra 安装包弄到 sandbox。

### 方案对比（实测）

| 方案 | 耗时 | 传输量 | 评价 |
|---|---|---|---|
| **A. 本机下载 → SSH 隧道传** | 15 分钟才到 13% | 1088 MB（翻倍） | ❌ 慢且浪费 |
| **B. 目标机直接 curl** | 约 3 分钟 | 544 MB | ✅ **最优** |

### 为什么 A 这么慢

```
本机 ──下载(544MB)──→ 本机磁盘
本机 ──SSH 隧道────→ 目标机
```

1. **传输量翻倍**
2. SSH 隧道带宽远低于直连
3. 隧道还要处理 proot 的 ptrace 开销

### 结论

**能在目标机直连下载，就绝不要中转。**

只有当**文件不在公网**（本地私有文件）时，才需要中转。这时要：
1. 先问清楚用什么通道
2. 加 `ServerAliveInterval`
3. 校验 md5/sha256

## 案例 5：识别假的内存上限

### 现象

```bash
$ cat /sys/fs/cgroup/memory.max
max                          # 看起来无限制

$ python3 -c "import mmap; m = mmap.mmap(-1, 8*1024**3); print('8GB OK')"
8GB OK                       # 真的能分配
```

**但实际跑大程序，5 GB 就被杀。**

### 为什么

- `mmap` 只是**预留地址空间**，不分配物理页（lazy allocation）
- 只有**真正写入每个页**才会触发物理分配
- OOM killer 在物理页耗尽时才动手

### 正确测法

```bash
python3 - <<'EOF'
CHUNK = 256 * 1024 * 1024
kept = []
try:
    for i in range(1, 100):
        b = bytearray(CHUNK)
        for off in range(0, len(b), 4096):   # 关键：逐页触碰
            b[off] = 1
        kept.append(b)
        print(f"{i*256} MB OK", flush=True)
except MemoryError:
    print("MemoryError")
EOF
echo "exit=$?"      # 137 = SIGKILL
```

### 教训

**永远用实测，不要相信 cgroup 的数字。**

## 案例 6：备份必须验证

### 现象

备份了 rclone 源码包，上传到云盘，校验 md5 一致。
后来需要恢复时，**解包编译失败**。

### 根因

```
包里的 remote_cfg_template.go   365 行（旧版）
源码里的                          394 行（新版）
```

模板文件没同步。md5 校验只能证明**传输没损坏**，不能证明**内容正确**。

### 正确做法

```bash
# 1. 解包
mkdir /tmp/verify && tar xzf backup.tar.gz -C /tmp/verify

# 2. 真实编译验证
cd /tmp/verify && ./build.sh

# 3. 检查产物
ls -lh output_binary
strings output_binary | grep -F 'expected_marker'

# 4. 通过才算备份成功
```

### 教训

> **只备份不验证 = 假备份。**
>
> md5 相同 ≠ 内容可用。
> 必须**实际跑一遍构建流程**，能产出可用二进制才算数。

## 通用经验总结

| 领域 | 经验 |
|---|---|
| 内存 | 实测上限；无 swap 要留余量；`-Xmx` 用 0.7 倍 |
| CPU | 留 1 核给 sshd，否则失联 |
| 权限 | `CapEff=0` 就用 proot；OpenSSH 换 dropbear |
| 解包 | 版本要够新；参数查文档别自己拼 |
| 传输 | 目标机能直连就别中转 |
| 备份 | 必须实测可恢复 |
| 长任务 | `setsid nohup ... < /dev/null &` 或 tmux |
| 排查 | 先看 `dmesg`（OOM）、`ps`（状态）、`-v 9`（proot） |
