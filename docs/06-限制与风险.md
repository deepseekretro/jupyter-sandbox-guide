## 硬限制清单（实测）

### 内核态能力

| 操作 | 结果 | 原因 |
|---|---|---|
| `chroot /tmp /bin/true` | `Operation not permitted` | 无 `CAP_SYS_CHROOT` |
| `mount -t tmpfs none /mnt` | `permission denied` | 无 `CAP_SYS_ADMIN` |
| `sysctl -w net.ipv4.ip_forward=1` | `Read-only file system` | `/proc/sys` 只读 |
| `unshare -U` | 可能 `Operation not permitted` | seccomp 拦截 |
| `iptables` | 失败 | 无 `CAP_NET_ADMIN` |
| `setuid` 二进制 | 无效 | 宿主不允许 |
| `docker` | 失败 | 需要特权 |
| 加载内核模块 | 失败 | 需要特权 |

### 能力位实测

```bash
$ grep -E "CapEff|CapBnd" /proc/self/status
CapEff:  0000000000000000
CapBnd:  00000000a80425fb
```

**`CapEff = 0`** —— 即使 `id` 显示 `uid=0`，**一个能力都没有**。

### seccomp

```bash
$ grep Seccomp /proc/self/status
Seccomp:        2
Seccomp_filters: 2
```

`Seccomp: 2` = `SECCOMP_MODE_FILTER`，syscall 被过滤。触发的 syscall 返回 `EPERM` 而非崩溃。

### 资源类

| 项 | 实测 | 备注 |
|---|---|---|
| `/dev/shm` | 64 MB，`noexec` | **不能执行二进制，不能放大文件** |
| swap | 无 | OOM 直接 SIGKILL |
| 嵌套虚拟化 | 不可用 | KVM 需要特权 |

**`/dev/shm` 的坑**：很多程序默认往 `/dev/shm` 写临时文件（PostgreSQL、Chrome、Java）。64 MB 很容易满。

```bash
# 检查
df -h /dev/shm

# 规避：改 TMPDIR
export TMPDIR=/tmp
```

## 服务条款风险

### ⚠️ 必须知道的事

在线服务的 ToS 通常**禁止或限制**：

| 行为 | 常见条款 |
|---|---|
| 挖矿（cryptomining） | 几乎全部禁止 |
| 长期跑代理/VPN | 多数禁止 |
| 端口扫描/渗透 | 全部禁止 |
| 存储/分发盗版内容 | 全部禁止 |
| 转售资源 | 全部禁止 |
| 长时间 100% CPU 占用 | 部分禁止（"合理使用"条款） |
| 跑公网服务 | 多数禁止 |

### 现实中的封号原因

| 原因 | 触发方式 |
|---|---|
| CPU 长期满载 | 监控告警 |
| 异常网络流量 | 出站流量大 |
| 端口扫描 | IDS 检测 |
| 可疑出站连接 | 灰名单 IP |
| 多账号 | 关联识别 |

### 本文档的立场

> **本文档只讲技术原理，不构成使用许可。**
>
> 是否允许长时间占用、是否允许跑服务、是否允许特定用途，
> **以你使用的服务方 ToS 为准**。请自行确认。

**合理的用法**：
- 学习、实验、原型开发
- 短期的批量计算
- 数据处理分析

**明确不适合**：
- 把免费额度当免费 VPS 长期挂服务
- 跑与"数据科学"无关的重负载
- 任何商业转售

## 安全边界

### ⚠️ 不要假设隔离

**你在容器里，但容器不等于安全沙箱。**

| 误判 | 现实 |
|---|---|
| "我在自己的容器里，随便存密钥" | 容器可能被服务方运维访问 |
| "这机器只有我一个人" | 同宿主的其他容器可能通过侧信道攻击 |
| "文件删了就没了" | overlay 下层可能有快照 |
| "网络是隔离的" | 同宿主容器共享网络命名空间（有时） |

### 密钥管理

```bash
# ❌ 绝对不要
echo "API_KEY=sk-xxxxx" > /root/key.txt     # 明文落盘
git commit -m "add key"                      # 提交密钥

# ✅ 正确
# 1. 用环境变量（进程内，不落盘）
export API_KEY=xxx

# 2. 用后即删
unset API_KEY

# 3. 敏感文件 0600
chmod 600 /root/.ssh/id_ed25519
```

### 共享密钥的坑

如果多个机器用**同一个 SSH key**：

```
机器 A ──┐
机器 B ──┼── 同一个 id_ed25519 ──→ 服务端
机器 C ──┘
```

**结论：不能随便换这个 key** —— 换一台会影响所有机器。要么统一轮换，要么建新的独立 key。

> 实测教训：曾想换共享的 frpc 密钥，发现多台机器依赖它，只能放弃。

## 性能陷阱

### proot 的 syscall 开销

实测 CPU 分布：

```
%Cpu(s): 39.4 us, 43.9 sy, 15.2 id
```

**`sy`（内核态）占 43.9%** —— 这是 proot 的 ptrace 拦截开销。

**影响**：
- I/O 密集程序慢 30-60%
- 纯计算几乎无感
- 大量小文件操作很慢

**缓解**：
- 用 `-b` 绑定热点目录
- 减少小文件 I/O
- 把数据打包成单个大文件

### 反编译器/分析器的内存陷阱

以 Ghidra 为例：

| 现象 | 原因 |
|---|---|
| 分析 52 MB 二进制 OOM | 12 万函数，需 >5 GB |
| 默认堆只有 2 GB | 不够 |
| 设 `-Xmx` 太大 | 堆外内存 + 堆 > 容器上限 → OOM |

**正确做法**：`-Xmx` = 可用内存 × 0.7

### 并行度陷阱

```bash
# ❌ 4 核全占 → sshd 抢不到 CPU → SSH 失联
make -j$(nproc)
java -XX:ParallelGCThreads=4 ...

# ✅ 留 1 核
make -j3
```

**实测事故**：labs-01 上 6 路并行 Ghidra 把机器压死，**SSH 彻底失联**，只能等 OOM 自己杀。

## 合规的使用姿势

| 场景 | 建议 |
|---|---|
| 学习 Linux | ✅ 完全没问题 |
| 编译开源软件 | ✅ 没问题 |
| 数据分析 | ✅ 服务方的本意 |
| 原型验证 | ✅ 没问题 |
| 跑几天的大计算 | ⚠️ 看 ToS 的"合理使用" |
| 长期挂服务 | ❌ 多数禁止 |
| 当 VPS 用 | ❌ 明确禁止 |

**判断标准**：如果服务方的运维看到你的用法会觉得"这人正常在用"，就没问题。

## 检查清单

动手前过一遍：

- [ ] 确认了 `CapEff`（决定要不要 proot）
- [ ] 确认了真实内存上限（实测，不信 cgroup）
- [ ] 确认了 swap 状态（无 swap 要格外小心）
- [ ] 确认了持久卷路径
- [ ] 确认了 `/dev/shm` 大小和挂载选项
- [ ] 读过 ToS（至少扫一眼禁止条款）
- [ ] 不在容器里存明文密钥
- [ ] 长任务用 `setsid nohup` 或 tmux
- [ ] 并行度留了余量给 sshd
- [ ] 有备份方案且验证过

## 小结

| 类别 | 硬边界 |
|---|---|
| 内核态 | chroot/mount/sysctl/iptables/docker **全不可用** |
| 资源 | `/dev/shm` 64MB noexec；无 swap |
| ToS | 挖矿/代理/扫描/长期满载 **基本都禁** |
| 安全 | 容器 ≠ 安全沙箱；不存明文密钥 |
| 性能 | proot 的 `sy` 开销 40%+；并行度要留余量 |
